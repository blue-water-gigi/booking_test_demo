### Critical

1. Отсутствие валидации входных данных с клиента. Необходимо внедрить валидацию через FormRequest.
2. В store() потенциальная SQL-инъекция, т.к. данные передаются прямо из запроса без валидации, без параметров.
   Необходимо использовать Eloquent или Query Builder, либо параметризировать запросы.
3. В store() на строке 37 передаётся вся информация из Request, т.к. user_id разрёшен к заполнению в fillable Bookings,
   то любой юзер может создать бронь от лица другого. Юзера нужно брать из $request->user() либо из фасада Auth::user().
4. В destroy() любой аутентифицированный юзер сейчас может удалить чужую бронь. Необходимо ввести политику для
   авторизации юзера и проверки его прав. Также это можно сделать через middleware.

### Major

1. N+1 проблема в today(), т.к. мы обращаемся к отношению room и после проходимся по каждому отношению через map. Для
   eager loading необходимо использовать with(), если контракт с клиентом существует.
2. Сейчас в store() пересечения не допускаются, т.к. равенство в запросе, в том числе строгое. Необходимо поменять >=
   на > и <= на <.
3. В store() сейчас race condition. Чтобы убрать можно использовать транзакцию с блокировкой комнаты.
4. В today() методе сейчас в whereDate() передаётся today(), который возвращает время по UTC. Т.к. у нас по условию
   часовые пояса Москвы и Новосиба, то лучше строить границы времени исходя из таймзоны конкретного офиса.
5. Логика бронирования завязана на таймзонах, но в миграциях мы используем обычные timestamp в UTC. Скорее всего нужно
   конвертировать значения из БД в часовой пояс конкретного офиса. Стоит также рассмотреть вариант в timestampTz.

### Minor

1. Отсутствие типизации и declare(strict_types=1). Необходимо добавить типизацию. Для объявления strict_types можно
   использовать rector либо изменить шаблоны создания классов через artisan и добавить туда по умолчанию strict_types
2. Использование фасадов прямо в контроллерах. Допустимо, но предпочтительно оформить через DI. В случае с обращением к
   БД - репозитории. В случае с логами - через логгер интерфейс в DI.
3. Возвращение пресных json через response()->json(). Допустимо, но предпочтительнее ввести ресурсы и коллекции и
   отдавать клиенту типизированные данные по соглашению.
